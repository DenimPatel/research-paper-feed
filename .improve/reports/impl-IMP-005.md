## 2. Approach

### 2.1 `web/vite.config.ts` — three lines

```diff
   test: {
-    environment: "node",
-    include: ["src/**/*.test.ts"],
+    environment: "jsdom",
+    include: ["src/**/*.test.ts", "src/**/*.test.tsx"],
+    setupFiles: ["src/test-setup.ts"],
   },
```

This is criterion 2 of the spec verbatim (`environment: "jsdom"`, both globs) plus one
`setupFiles` line.

### 2.2 Why a global jsdom environment, with no per-file overrides

The brief suggested per-file or per-project overrides might be needed to keep the `.ts` lib tests
in a node-ish environment. **They are not needed, and I verified this rather than assuming it.**
The 39 pre-existing lib tests pass under *both* environments:

* under `environment: "jsdom"` — the committed configuration, `npm test` → 39/39 pass;
* under `environment: "node"` — reproduced in a throwaway `/tmp` copy of the tree, `npm test` →
  39/39 pass, only the new `.tsx` file failed.

The reason is that none of the three lib suites depend on a *missing* DOM:

* `collections.test.ts` injects its own `MemoryStorage` / `THROWING_STORAGE` fakes (`:32-79`) and
  never reads `window.localStorage`, so a real `localStorage` existing alongside is inert;
* `paperIndex.test.ts` stubs global `fetch` and asserts on it — environment-independent;
* `search.ts` is pure string/number logic.

So the smallest change that satisfies criterion 2 literally is also the safe one, and no existing
test file was edited at all. Adding three `// @vitest-environment node` docblocks or a
`vitest.workspace.ts` two-project split would have been three extra files of churn for no
behavioural gain, and both would have *deviated* from the spec's literal wording.

This also keeps the door open for a later `node:fs` fixture test (see §7).

### 2.3 `web/src/test-setup.ts` — why it is needed at all

`web/package.json` runs `vitest run` and the repo does not set `test.globals`, so Vitest's
`afterEach` is **not** a global. `@testing-library/react` v16 auto-registers its cleanup hook by
probing for a global `afterEach`; with `globals: false` that probe fails, so every rendered tree
would silently leak into the next test's `document` and make all five downstream component-test
items (IMP-037, IMP-129…132, IMP-018) order-dependent and flaky.

```ts
import { cleanup } from "@testing-library/react";
import { afterEach } from "vitest";

afterEach(cleanup);
```

I chose a `setupFiles` entry over flipping `test.globals: true` deliberately: `globals: true`
would inject ~20 undeclared globals into the scope of *every* test file including the three
existing pure-logic suites, where a typo'd or missing `import { describe }` would then typecheck
and run instead of failing loudly. A setup file is explicit and costs one 3-line file.

The file is named `test-setup.ts`, which does **not** match the `src/**/*.test.ts` include glob,
so Vitest cannot mistake it for a suite.

### 2.4 The smoke test — placement, and why it is not IMP-037

The brief required at least one smoke component test; the spec's own criterion 3 says "no component
test yet — that is IMP-037". These conflict, and I resolved it in favour of the brief (more
recent, more specific) while **not stealing IMP-037's deliverable**:

* IMP-037 owns `web/src/components/__tests__/PaperCard.test.tsx` (spec line 696) and asserts the
  title link's `href` equals the fixture `absUrl` and that the publication date renders.
* I put the proof at `web/src/__tests__/domEnvironment.test.tsx` instead — a location the profile
  and the backlog already bless for non-mirrored tests (spec line 392 uses
  `web/src/__tests__/` for the `ErrorBoundary` test) — and asserted only *environment* facts
  (a DOM exists, a component mounts into it, trees are unmounted between tests). I deliberately
  did **not** assert `PaperCard`'s `href` or date rendering, so IMP-037 still has real work to do.

The fixture is a minimal complete `Paper` literal typed as `Paper` from `web/src/lib/types.ts`, so
a future field addition to the wire schema will surface as a typecheck error here rather than
silently.

## 3. New dependencies and justification (profile §6 requires this in writing)

Added with `npm install --save-dev jsdom @testing-library/react @testing-library/user-event`.
All three are `devDependencies`; `react` and `react-dom` remain the **only** runtime
`dependencies`, and the production bundle is byte-for-byte the same size (§5).

| Package | Resolved | Why |
| --- | --- | --- |
| `jsdom` | `29.1.1` | Provides the DOM `document`/`window` that criterion 2 requires. Vitest's `environment: "jsdom"` loads it as an optional peer — `npm ls` shows it deduped under both the root and `vitest@2.1.9`. Dev-only; never bundled. |
| `@testing-library/react` | `16.3.3` | The canonical React renderer for `render()` / `screen` / `cleanup`. Name criterion 1 requires. Pulls `@testing-library/dom@10.4.2` as an auto-installed peer (recorded in the lockfile, so `npm ci` reproduces it). |
| `@testing-library/user-event` | `14.6.7` | Name criterion 1 requires. **Currently unused by the smoke test** — see the caveat below. |

**Security-surface cost:** none shipped. `web/package-lock.json` is consumed by `npm ci` in
`.github/workflows/ci.yml:31` and `.github/workflows/deploy.yml`, but only `react`, `react-dom`
and their transitive deps reach the Pages bundle; a dev-only test harness cannot execute in a
visitor's browser. `npm audit` reports the **same 5 vulnerabilities as the PE-1 baseline**
(3 moderate, 1 high, 1 critical — all in `vite`/`vitest`/`esbuild`/`vite-node`, all pre-existing);
the install introduced **zero** new advisories. Nothing was auto-fixed, so no dependency was
silently bumped.

**Caveat on `@testing-library/user-event` — flagged, not resolved.** The spec's own Notes say
"If `@testing-library/user-event` proves unnecessary for the first smoke test, drop it rather than
carrying an unused dep", which contradicts acceptance criterion 1, which names all three
packages. I followed **criterion 1**, because acceptance criteria are the graded contract and the
Notes are advisory, and because five queued items (IMP-129…132 plus IMP-018) will need real
pointer/keyboard simulation that `fireEvent` does not model faithfully. It is currently carried
but unimported. **If a reviewer prefers the Notes, the removal is a one-line
`npm uninstall @testing-library/user-event` plus a lockfile regen and nothing else** — no test or
config file references it.

## 7. Uncertainty, caveats, and things I did not do

1. **`jsdom@29` engine range vs. CI's Node 20.** `jsdom@29.1.1` declares
   `engines: {"node": "^20.19.0 || ^22.13.0 || >=24.0.0"}`. Both workflows pin
   `node-version: "20"` (`.github/workflows/ci.yml:29`, `.github/workflows/deploy.yml:38`), which
   floats to the newest 20.x — currently ≥ 20.19.0, so the range is satisfied. I could **not
   verify this empirically**: every Homebrew `node@21` / `node@22` keg on this machine is a symlink
   into `/opt/homebrew/Cellar/node/25.6.1`, so there is no real Node 20 available here. Because
   there is no `.npmrc` and no `engine-strict=true`, npm treats a mismatch as an `EBADENGINE`
   *warning*, not an install failure, so `npm ci` would not break even in the worst case.
   **Mitigation if CI ever warns:** `npm install --save-dev jsdom@^26`, which declares
   `node >=18`. I chose not to pre-emptively downgrade: criterion 1 asks for `jsdom` unversioned,
   the range is satisfied by CI's actual resolved Node, and it works locally.
2. **Test wall-clock grew ~1 s.** The suite went from ~0.31 s to ~1.20 s, almost entirely jsdom
   teardown (`environment 2.6s` in vitest's own breakdown). For 42 tests that is irrelevant; a
   future item that finds it annoying can split into two vitest projects, which is why I noted in
   §2.2 that the lib tests are environment-agnostic.
3. **`@testing-library/user-event` is installed but unimported** — see §3. Flagged for the reviewer
   rather than silently resolved in either direction.
4. **`@testing-library/dom` is not in `package.json`.** It is a peer dependency of
   `@testing-library/react@16` that npm 11 auto-installed and recorded in the lockfile, so
   `npm ci` reproduces it deterministically. It is not hand-added. If the project ever wants it
   pinned explicitly, that is a deliberate `npm install -D @testing-library/dom` decision, not
   something this item should do.
5. **No `@testing-library/jest-dom`.** The spec did not ask for it and nothing needs it; the
   smoke test uses plain `expect(...).toBeTruthy()`. Adding it would be a fourth dependency.
6. **`test.globals` left `false`.** Deliberate; see §2.3.
7. **I did not run the Playwright visual pass.** Per profile §4.2 that row applies to
   `App.tsx` / `components/**`, neither of which I touched; this is profile §4.1 (`lib/**` +
   tooling). I substituted the dev-server HTTP 200 check plus the byte-identical bundle hashes
   (§4) as direct evidence that nothing visible changed. **`.improve/artifacts/` was not written
   to.**
8. **Stale premise spotted in the backlog, reported not fixed** (`.improve/FEATURES.md` is
   do-not-touch for me): the Notes of the fixture-contract item at `.improve/FEATURES.md:1662`
   justify `node:fs` in `paperIndex.test.ts` with *"legal because `vite.config.ts:8` sets
   `environment: \"node\"`"*. That half of the sentence is now false. The test would still work —
   Vitest runs on Node in every environment and only swaps globals, so `node:fs` remains
   importable under jsdom, and my `/tmp` run (b) confirms the lib suites pass under jsdom — but the
   stated justification needs updating when that item is picked up. Same class of staleness as the
   IMP-003 verifier's WEB-01 note.
9. **Baseline drift acknowledged.** The profile's §3.3 "36 tests" and criterion 3's "36" are both
   stale; the real pre-change baseline I measured was 39, and every count in this report is against
   that measured 39.
