## 2. Scoring, argued

The brief asked for the arguments to be made rather than asserted. Each item's Notes carries the
full argument; this is the summary.

**Items 1–4 look trivial and are not, so they sit at 20.0 / 20.0 / 15.0 / 10.0** — the same band
as the existing top items. The argument is not that bookkeeping is high-impact in the product
sense. It is:

* **Confidence is 5 across all four**, and that is not an estimate. Every figure cited was
  re-measured in this session against the actual files. `impact × 5 ÷ 1` puts a `S`-effort item at
  5× its impact.
* **Each one actively misleads the next worker rather than merely omitting something.** That is
  the distinction from ordinary tidy-up. `FEATURES.md:29-33` is the block a verifier reads to
  decide whether a failure is pre-existing; with `44 tests OK` and `69 tests across 5 files` on
  screen, a real regression of the 119-test suite reads as pre-existing, and a pre-existing failure
  reads as new work. `REPO_PROFILE.md:862` presents a fixed defect as open. A missing `PROGRESS.log`
  row means an item marked DONE has no SHA anyone can audit. Misordered tier headers send a reader
  to the wrong section of a 3,782-line file. In each case the cost of leaving it is a **wrong
  conclusion**, not a cosmetic one.
* **Why they are differentiated rather than all set to 20.0.** Inflation is its own defect, and
  these four are not equally harmful. IMP-221 scores 20.0 (impact 4) because its block gates
  regression verdicts in both directions. IMP-222 scores 20.0 (impact 4) for the same reason plus a
  wrong *defect* row, which is worse than a wrong count because a reader treats an open-defect row
  as authoritative. IMP-223 scores 15.0 (impact 3) because three of its four gaps are already
  visible in the log's free text — the record is partially traceable today, IMP-203 is the one that
  is not — and because the durable deliverable is the reconciliation check, not four rows.
  IMP-224 scores 10.0 (impact 2) because it is purely structural: no claim in the file is false,
  no verdict changes, and the file remains readable. Calling it 20.0 would be inflating the
  backlog's top band to include a heading-level tidy-up.

**The self-staleness design constraint, and which mechanism is specified.** The brief forbids a
retyped literal, because the numbers change on every item added or flipped to DONE, so a
corrected constant is wrong again within one commit. Two shapes were available:

1. **A generator/script that recomputes the header from the file.**
2. **Removal of the counts in favour of a pointer to a command that prints them, plus a check that
   fails when they disagree.**

**Both are specified, with the generator as the mechanism and the check as the guarantee**, and
the reasoning is recorded in IMP-221's Notes. The generator alone is insufficient, because it only
runs when someone remembers to run it — that is precisely the failure that produced `212`. The
pointer alone is also insufficient, because a reader who does not know to distrust the header will
read the figure at a glance, which is what the current design invites. What closes the loop is the
`--check` mode: derived-versus-stated comparison that exits non-zero on disagreement, so the figure
cannot be wrong silently even if the generator is never invoked. Both branches of IMP-221's
criterion 3 are marked acceptable provided **no second hardcoded copy exists anywhere** — not in the
script, not in a comment, not in the item — and criterion 4 requires proving the check can go red.
IMP-222 criterion 2 requires the profile to adopt the *same* mechanism as IMP-221 and is
`Depends on: IMP-221`, so the loop ends up with one mechanism rather than two that disagree.

**IMP-225 is a defect in the verification apparatus and is scored as one — 10.0 (impact 4,
confidence 5, effort M).** Impact 4 rather than 5, argued: nothing a reader sees is wrong, no
product code is wrong, and no data is at risk. The apparatus is not lying, it is *unproven* — a
gate that cannot reproduce its own baseline is not a gate. 4 is the honest number because the harm
is total loss of confidence in a load-bearing check (`FEATURES.md:42-43` is part of every item's
stated Verification method), not a wrong output. Impact 5 is reserved for the items that are
breaking the deploy today. The consequence of the arithmetic is stated in the Notes so it is not
mis-read as low priority: `4 × 5 ÷ 2 = 10.0` places it in Tier 10.0 **only** because the deliverable
is a measurement plus a decision rather than a fix, and it must not be triaged last because the
number is lower than a cosmetic heading fix's neighbours.

**IMP-226 is a discovery round, so its score is a bound, not a measurement — 8.0 (impact 4,
confidence 4, effort M).** Confidence is 4, not 5, and that is the honest part: the *existence* of
the gap is measured (0 of 217 titles across four search terms, no category, 3 contributor-facing
onboarding items), but whether the unowned surface is large or small is exactly what the round
exists to find — a discovery item cannot claim maximum confidence on a claim it is designed to
test. Impact 4 because the entire first-run surface for a repo with two CLIs and a web app is
unowned. The Notes state explicitly that 8.0 is a **floor**: the round is guaranteed to produce
grounded items or an argued finding, and anything above that is upside not counted in the score.

## 3. Method, and how the file was not re-broken

`FEATURES.md` has been corrupted once already — a script used
`re.split(r'\n(?=### IMP-)', txt)` and rejoined with `"".join(...)`. That pattern **consumes the
newline**, so 208 item headings were glued onto the previous line and four freshly-filed items
were destroyed; the repair is commit `4a39b84` (`chore(improve): repair the newline loss in
FEATURES.md [IMP-030]`).

This round did **not** split-and-rejoin at all. Each item block was inserted by a single
`str.replace(anchor, new_block + anchor, 1)` against a unique anchor line — a pure insertion at a
known offset, with no rejoin step in which a newline could be consumed. The safe zero-width form
`re.compile(r'(?m)^(?=### IMP-)')` was used for the *verification* pass only, where the text is
read and discarded rather than written back.

Anchors used, each a unique full item heading line:

| Insert before | Items added | Enclosing tier |
| --- | --- | --- |
| `### IMP-173 — Stop a JSON` | IMP-221, IMP-222 | `## Tier 20.0` (`:250`) |
| `### IMP-220 — Make \`dedupe_records\`` | IMP-223 | `## Tier 15.0` (`:857`) |
| `### IMP-148 — Announce the empty states` | IMP-224, IMP-225 | `## Tier 10.0` (`:2128`) |
| `### IMP-178 — Log the soft shard failure` | IMP-226 | `## Tier 8.0` (`:2827`) |

Placement rule followed: adjacent to items of the same Priority score, ignoring the tier headers
as placement guides (they are themselves the subject of IMP-224). Each new item's score equals its
enclosing tier header's score, which is the invariant IMP-224's criterion-5 check will enforce.
