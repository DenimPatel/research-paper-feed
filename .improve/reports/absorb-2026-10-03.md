## 1. Findings filed

### IMP-216 — Stop a deep-offset arXiv 500 from deleting a category the index already holds (12.5, bug-fix, depends on IMP-204)

Source: `discovered-IMP-030.md` D-1. The highest-value finding of the round and a
**live production defect**: two consecutive full production builds of the bare
`deploy.yml:117` command both lost `cs.AI` to a reproducible HTTP 500 at
`start=10000`, while `cs.LG` reached `start=9000` and `cs.CV` stopped at
`start=6000`. The client's 6 attempts over ~60 s all returned 500.

What I added beyond the discovery report, by measurement rather than inference:
**the failure is not merely lossy, it is false.** A local stub
(`/tmp/rpf-absorb/probe_partial.py`, a fake `iter_results` yielding three `cs.AI`
records then raising `arxiv.ArxivError`, run through `build_index.main`) produces:

```
exit 0
manifest.categories        ['cs.CV', 'cs.LG', 'cs.CL', 'cs.RO']
manifest.failedCategories  ['cs.AI']
manifest.totalPapers       7
failed-category ids present in shards: ['2601.00000', '2601.00001', '2601.00002']
```

So the deployed site drops the `cs.AI` chip (`build_index.py:497`) **and** renders
`"cs.AI could not be fetched from arXiv … so it has no papers here and no filters
to browse"` (`web/src/lib/failureCopy.ts:103-110`) while the index holds every
`cs.AI` record the run collected before the failure. The item makes that
classification the centre of the fix, which is what makes it `M` and not `S`.

**Why the fix cannot be "retry more", stated in the item's criterion 3:** the fault
is persistent at a given offset and the offset *moves* — it is a function of how
many in-window papers a category holds, so pinning it would pin a number arXiv
will invalidate. Criterion 3 therefore bounds the **depth** (largest `start` the
deploy can request, asserted through the file's existing `requested_pages` helper)
rather than the attempt count.

**Two collisions the item forces into the open rather than papering over** — both
found by reading the current tests:

- `tests/test_build_index.py:1034-1056`
  (`test_the_cap_stays_clear_of_the_real_window_sizes`) requires the deploy cap to
  be ≥ 2 × the largest measured 60-day window (21,570), while any budget that keeps
  a 10,785-paper `cs.AI` off `start=10000` is **below** that. Two pinned
  invariants cannot both hold, so criterion 4 requires the collision to be
  resolved explicitly (one assertion may move, with the papers-lost cost argued),
  never by deleting a test.
- `tests/test_build_index.py:603` currently pins
  `failedCategories == [cs.AI]` for a category that yielded a record — i.e. it
  pins the false classification. Risk is `med` for exactly that reason.

**Cross-referenced, not duplicated:** IMP-204 (DONE — owns the partial-index
contract this amends, its exit-code policy is untouched), IMP-095 (`UNLIMITED`),
IMP-206 (deploy-workflow pin pattern), IMP-205 (criterion 6 changes *its input*,
the measured page count, not its derivation), IMP-183 (**explicitly not** the fix:
`cs.AI` held 10,785 papers *inside* the 60-day window, so a date-bounded query
still needs 11 pages and still asks for `start=10000` — I corrected the brief's
"reduces the page count for the same reason" framing in the item's Notes), IMP-208
(arXiv does not space its retries).

**On the score.** Impact 5, confidence 5, effort `M` → `5 × 5 ÷ 2 = 12.5`, which
is the arithmetic ceiling for an `M` item and therefore *not* a statement about
severity. The brief asked for the top band (max 20.0); scoring this 20.0 would
require either `effort = S`, which is not honest (Python classification + the
`web/` copy + three test files + two workflow comments + a readme paragraph), or a
silently lowered impact. The item's Notes instead say it should be triaged as
though it sat in the 20.0 band, following IMP-204's own instruction that of the two,
it goes first.

### IMP-219 — Recapture the README hero from a default 60-day index build (10.0, docs, depends on IMP-216)

Source: the IMP-030 verification. The shipped `images/feed_example.png` was
captured from a `--retention-days 30` index — a documented workaround for D-1, not
a fix — so the hero reads `14,253 papers` against the deployed default build's
25,761 / 25,759, twenty lines above `readme.md:31`'s "rolling 60-day window"
claim. Dependency on IMP-216 is the honest constraint: while `cat:cs.AI` fails at
depth, no complete capture exists without the 30-day workaround, so recapturing now
would just reproduce the defect. Criterion 3 requires stopping and reporting rather
than shipping a partial capture, and criterion 1 requires the hero's number to match
`totalPapers` in the manifest that produced it. Effort `S`, but the verification is
one full arXiv build (~2–5 min healthy), explicitly not a smoke run.

   the query reduces the page count "for the same reason". It reduces *total*
   results, but not `cs.AI`'s depth: its 60-day window alone is 10,785 papers, so
   the faulting `start=10000` is still requested. IMP-216's Notes say so; IMP-183's
   own entry may want the same caveat added.
